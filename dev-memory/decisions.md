| D-062 | 2026-11-17 | **Speech bubble lifetime.** The bubble stays **max(8 s, 90 ms per character)**, counted from when the last character is shown (the reply's total length sets the time), then fades over 400 ms. **Hovering** the bubble pauses the countdown (it resumes with what was left, at least 1.5 s). A **click pins** the bubble: no countdown until it is clicked again or a new message is sent (a new message removes it). A pinned, finished bubble stays while the input is open. An interrupt leaves the text shown so far on screen with the normal countdown from its length (a filler or nothing shown is hidden; panic hides everything). The values are `BubbleTuning` in `Character/ChatTuning.cs`. Replaces the 6 s / 60 ms-per-character fade of step 2 (architecture doc only, no earlier decision) | Philip's request after testing step 2 by hand: the old fade started when the stream ended, which with a typewriter display would cut long replies short, and a reader needs to stop the clock | ACCEPTED |
| D-063 | 2026-11-17 | **Typewriter display.** Reply text is revealed at a steady pace instead of as raw stream chunks: 45 characters/s, rising gradually when text is buffered (+0.5 cps per buffered character beyond 60, capped at 200 cps) so long replies do not drag; pauses of 260 ms after `.` `?` `!` and 110 ms after `,` `;` `:` (only when followed by a space or the end of the text, so `3.5` and `...` pause once at most). The first character is shown at once when the first chunk arrives, so first-word timing is unchanged. An interrupt drops what is not yet shown (text stops where it is; the history still keeps what the brain had produced). The timer (`ReplyTypewriter`, 33 ms) runs only while text is waiting to be shown and is stopped otherwise, so it costs nothing in idle. The pacing is pure logic in `TypewriterPacer` with unit tests; all values are `TypewriterTuning` in `Character/ChatTuning.cs`. Filler lines are not paced | Philip's request after testing step 2 by hand | ACCEPTED |
